   531	- **Resolve before judging (T-22 DoD 1/2).** Every path claim is first resolved against a
   532	  `PathUniverse` built from the four sources that can name a path: the supplied patch, the git
   533	  diffstat, the truncation manifest, and `git ls-tree -r HEAD` at the reviewed commit. The
   534	  worktree filesystem is deliberately **not** a source: an untracked or gitignored file is not in
   535	  the commit the reviewer saw, so counting it let a file missing from the commit be labelled a
   536	  review-input omission instead of an evidence gap (round-2 finding 3). A bare name is matched by
   537	  basename against the whole universe *before* any exact root match is accepted, so `README.md`
   538	  with both a root file and `verify-evidence/T-19/README.md` is ambiguous rather than silently
   539	  resolved to the root one (round-2 finding 1). Exactly one match is judged at that path; several
   540	  matches are `unchecked` with **every** candidate listed — the resolver never picks one; no match
   541	  and the claim was only a name is `unchecked` with the reason `no path could be resolved from the
   542	  claim`. `confirmed` is reachable only for a claim that was located **and whose path the
   543	  repository does not contain** at the reviewed commit. A path the repository contains is never
   544	  confirmed absent, even when the diff budget withheld it; a failed lookup cannot reach
   545	  `confirmed` at all. That is the invariant the tally prints.
   546	- **Three states, not one label (T-22 DoD 3).** `confirmed` alone conflated a review-input failure
   547	  with a Worker evidence gap, so each verdict also carries a state in its detail, the table's
   548	  `state` column and the review notes: `omitted-from-review-input` (present in the repository, but
   549	  the archived manifest says the diff budget did not carry it — the budget's problem, owned by
   550	  T-16, and not a reason to send work back to the Worker), `absent-at-reviewed-commit` (nothing to
   551	  supply, because nothing is in the repository at that commit — a real evidence gap),
   552	  `unresolvable-claim` (the checker cannot judge it), plus `undecided`, `present-in-repository` and
   553	  `supplied-in-full` for the other refuted/unchecked reasons. The statuses stay inside the frozen
   554	  `confirmed | refuted | unchecked` vocabulary: `omitted-from-review-input` is `unchecked` (the
   555	  repository contains the file, so absence cannot be confirmed), `absent-at-reviewed-commit` is
   556	  `confirmed`, and a failed lookup is `unchecked`. The states are extra wording inside the existing
   557	  notes/detail fields, which is the only route a label has without a contract-change request.
   558	- **The tally audits itself (T-22 DoD 4).** `review.json`'s summary line and the payload's
   559	  `Tally:` line break `confirmed` down by basis — `by path-resolution`, `by explicit-named-path`,
   560	  `by manifest-record`, `from a failed lookup` — so a human skimming `review.md` sees at a glance
   561	  whether a confident batch rests on resolved evidence or on names the checker could not place. The
   562	  last number is 0 by construction; if it ever is not, the resolver is broken. `review_payload.md`
   563	  also states the universe every verdict was resolved against (sources, counts, the commit SHA) and
   564	  gives each row its own `how it was resolved` and `where it was found` columns.
   565	- **Existence is not visibility.** A file that exists on disk does not refute "its hunks were not
   566	  supplied". Visibility claims are compared with the supplied patch and the truncation manifest;
   567	  `refuted` means the evidence was in fact supplied in full, `omitted-from-review-input` means the
   568	  repository contains it but the budget withheld it (`unchecked`, because DoD 2 reserves
   569	  `confirmed` for absence), `absent-at-reviewed-commit` is `confirmed` because there was nothing to
   570	  supply, and `unchecked` is used whenever neither can decide it (fail closed). A `refuted` claim
   571	  removes the finding and is logged (`review_absence_refuted`), but a verdict is never upgraded on
   572	  it: the round goes to `NEEDS_HUMAN`, not to `APPROVED`.
   573	- **Diff completeness.** Before the review ships, the harness compares the git diffstat with the
   574	  supplied patch (`git diff --numstat` vs the archived `patch.diff`): every changed file must
   575	  have a hunk body, and `git check-attr -a` is run for `-diff` / `export-ignore` on every changed
   576	  path. A hiding attribute this task introduced is a harness finding (and an additive
   577	  `review_diff_incomplete` build-log event); one that predates the merge-base is reported as
   578	  pre-existing and is not a reason to fail the run. A Worker cannot opt out of review by
   579	  configuring `.gitattributes`.
